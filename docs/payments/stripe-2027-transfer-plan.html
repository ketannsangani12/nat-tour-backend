1. Executive Summary

Today, every card and card-reader payment on the platform is created as a Stripe destination charge: the platform's PaymentIntent carries transfer_data.destination, application_fee_amount, and (capability permitting) on_behalf_of, and Stripe automatically splits and pays out the tour operator's share the moment the charge succeeds. The request is to change this for any booking whose tour date falls in 2027 or later: the full charge should land in the NAT platform account first, and the operator's share should move to their connected account through a separate, later Transfer — while every booking for a 2026-or-earlier tour date keeps working exactly as it does today.

The good news from this research: the codebase already has a working, battle-tested implementation of the target pattern. TransferPaymentService (used today for tour-guide/partner-package splits) already creates a plain platform charge, computes a payout amount, calls Transfer::create() separately, and can reverse that transfer independently on refund — all backed by a transfers ledger table. This plan is fundamentally about generalizing that existing pattern into the primary payment path for 2027+ bookings, not inventing a new one.

The work is not a one-file change. Because there is no single "create a payment" choke point — 20 call sites build PaymentIntent params, and ~100+ call sites build refund params, all independently — the practical path is: (a) finish centralizing the param-building (it is 90% centralized already, via buildConnectedPaymentData()), (b) add one authoritative "which mode does this booking use" resolver, gated on tour date, (c) branch the existing centralized builder and the refund/dispute code on that resolver's answer, and (d) fire the operator transfer synchronously, at the same moment a destination charge already pays out today — no scheduled job, no delay, no new webhook events. Section 7 details each piece; Section 9 sequences them into low-risk phases.

Scope confirmation This plan covers card and card-reader (Stripe Terminal) payments only, matching the request. It does not change how cash/check/other offline payment methods are recorded, and it does not touch the existing tour-guide gratuity payout system (tour_operator_staff.stripe_account_id) — that system already transfers-only and is unaffected. It does address the overlap with the existing partner-package three-way split, since that system already performs transfers today and shares its trigger points with the new engine (Section 7.3).
Confirmed — clean cutover, not a migration As of this writing (September 2026), no booking with a 2027 tour date has been sold yet — no tour operator has opened their 2027 calendar for sale. That removes the one piece of real complexity a mid-flight change like this usually carries: there is no historical 2027 destination-charge booking to reconcile, backfill, or dual-support. Every booking in the system today, and every booking that will be created before this ships, keeps running on the existing destination-charge structure completely unchanged, forever — the new deferred-transfer path only ever applies going forward, to bookings created after this ships whose tour date happens to fall in 2027+. The only real deadline is to have the wiring phases (Section 9) done before the first 2027 tour date is opened for sale on any tenant's calendar, whenever that turns out to be — not January 1, 2027 itself, which is irrelevant to booking dates.
Confirmed — Decision 1 resolved: transfer timing stays exactly as today Per business decision, the operator's share moves to their connected account immediately, synchronously, at the same moment a destination charge already pays out today — not deferred to the tour date or the cancellation window. This removes the scheduled-job/sweep design this plan originally proposed (old Section 7.3/9) entirely: there is no delay to manage, no "pending payout" state to sweep, and therefore no new transfer.* webhook handlers needed for async reconciliation either, since the transfer either succeeds or fails inline, in the same request, the instant the charge is confirmed. What changes for a 2027+ booking is purely which Stripe mechanism moves the money — an explicit, code-driven Transfer::create() call instead of Stripe's automatic destination-charge split — not when it moves. The reusable engine for this (TransferPaymentService::transferToOperator()/reverseOperatorTransfer() for non-partner bookings, transferSellingCommission()/reverseSellingCommissionTransfer() for a partner-package booking's selling tenant) is built and unit-tested as of this revision — see Section 7.3.

public function buildConnectedPaymentData(string $destinationId, int $feeAmountCents, ?string $statementDescriptor = null): array

3. Why This Is Changing

The request states the destination for 2027+ bookings should be "transfer instead of destination in the PaymentIntent," with funds landing at NAT first, using the same timing the platform already uses today — the operator is still paid as soon as the charge is confirmed, nothing about that changes. This plan's initial draft speculated that the motivation was settlement-timing risk on far-future travel (holding funds until closer to the tour date, to reduce clawback exposure on cancellations/disputes for trips booked many months out). That speculation is now superseded — confirmed business decision: timing stays exactly as it is today, only the underlying Stripe mechanism changes.

What actually changes, then, is purely mechanical: instead of one PaymentIntent with transfer_data.destination (where Stripe silently does the split as part of settling the charge), a 2027+ booking uses a plain platform charge followed by an explicit, code-driven Transfer::create() call made by the application itself, immediately, in the same request. This gives NAT direct visibility into and control over each payout as a first-class event in its own codebase and ledger (the transfers table already records every one, per-booking, going back to the existing partner-split feature) rather than an invisible side-effect of Stripe's own charge-settlement plumbing — likely valuable for auditing, reconciliation, or future flexibility, even though the money moves at the same moment either way today.

Resolved — Decision 1 See Section 12, Decision 1 and the callout in Section 1: the transfer fires synchronously, immediately after payment confirmation, with no delay and no scheduled job. Sections 4, 7, and 9 below reflect this as the shipped design, not a proposal.

5. The 2027 Gate — How a Booking's Mode Gets Decided

5.1 Date source

The tour's actual departure date is not tour_bookings_master.created_at — it is reached via tour_bookings_master.tour_slot_id → tour_slot_times.id, and tour_slot_times.date already carries a denormalized copy of the date (no need to join out to tour_slot_dates). This column is already loaded on the $info object at every PaymentIntent-creation call site, because it's needed for pricing/description text today — so the gate adds no new query.

Timezone correction (found during implementation) This section originally warned that the boundary check must convert through the tenant's timezone (tourOperator()->timezone), per the project's general date-handling rule. Building PaymentModeResolver (Section 7.1, now shipped) surfaced that this doesn't actually apply here: tour_slot_times.date is a plain SQL DATE column with no time-of-day component at all — it already is the tenant's own local tour day, not a UTC instant that needs converting. A bare lexical string comparison against '2027-01-01' is therefore correct and timezone-safe as shipped, with no conversion step needed. (The general project rule still applies elsewhere, to genuine timestamp columns — this is a narrow, verified exception for this one specific date source.)

5.2 Locking the decision at payment time

The mode must be decided once, at PaymentIntent creation, and stored immutably — not re-derived later from the booking's current tour date. Two reasons: (1) Stripe's params can't be retroactively changed on a completed PaymentIntent, so refund/dispute code must know which regime the original charge used regardless of what the booking looks like now; (2) a booking's tour date can change after payment (reschedule / switch-package flows) — if the date moves across the boundary, the original charge's settlement behavior must not silently change underneath already-completed money movement. Recommendation: persist the decision as a payment_mode enum column (Section 8) written at creation time and read by every downstream refund/dispute/reporting code path — never recomputed from the current tour date.

5.3 Combo / multi-package carts

A single cart checkout can produce multiple tour_bookings_master rows sharing one cart_id, each with its own tour_slot_id and therefore its own date — confirmed via BookingService::comboBookingsData() and the isComboBooking() helper. Because one PaymentIntent today only carries a single transfer_data.destination, a combo cart already assumes one primary settlement target per charge; this plan keeps that constraint rather than trying to split one PaymentIntent three ways.

Recommendation Evaluate all booking rows in the cart; if any row's tour date is ≥ Jan 1, 2027 (tenant-local), the whole PaymentIntent uses deferred mode. This is the conservative choice — it never lets a 2027 booking sneak through in destination-charge mode — at the cost of also deferring a 2026 line item that happens to share a cart with a 2027 one. The deferred-transfer step (which runs per distinct stripe_destination_id, see 7.3) can still pay out each package's own connected account independently and on its own schedule once triggered, which is actually more flexible than what a single destination-charge PaymentIntent could ever do for a mixed-operator cart.

6.7 Partner packages, traced precisely — what "partner" actually means here

Clarified directly by the business: a "partner package" is a package physically listed and sold through one tenant's own storefront (the selling tenant), but actually owned/fulfilled by a different tenant (the 3rd party). On a successful booking, three parties are paid: NAT keeps a service commission, the selling tenant keeps a selling commission, and the remaining ticket cost goes to the 3rd party. Tracing the real PaymentIntent-creation code end to end (StripeUtils::createStripeIntent(), fed by TourPackageService::getTourPackageSlotInfo()) resolves this cleanly:

  • transfer_data.destination on today's destination charge is tour_operators.stripe_destination_id — the SELLING tenant's own connected account — for every booking, identically whether or not it's a partner package. tour_packages.stripe_destination_id (the 3rd party's account) is a separate column, never used as the original charge's destination.
  • application_fee_amount on that same charge equals only NAT's own serviceCommission — it never folds in the selling tenant's commission.
  • Consequence: the destination charge's automatic transfer sends amount − serviceCommission to the selling tenant in one lump sum — which is ticket cost + the selling tenant's own commission, combined. Then, separately, TransferPaymentService::transferToPartner() sends the ticket-cost portion again, independently, to the 3rd party's tour_packages.stripe_destination_id, drawing from the platform's own Stripe balance (a plain, unscoped Transfer::create() call — confirmed via StripePaymentGateway::createTransfer(), no stripe_account option).
Correction — an earlier revision of this section was wrong The first pass at this design reused transferToOperator() for the selling tenant's payout, sending them the full amount − platformFees remainder — deliberately copying what the destination charge's automatic transfer does today, on the reasoning that current partner economics should be preserved as-is. The business then clarified the actual intended rule directly: the selling tenant is owed only their own configured "Partner Fee" (their selling commission) — nothing more — and when that fee is 0, the selling tenant receives nothing at all, with the full ticket cost going straight to the 3rd party. That correction is reflected below and in the shipped code; it also happens to fully resolve the double-disbursement concern the earlier draft could only flag, not fix.
Decision 5 & 6 — RESOLVED: correct partner-package transfer design For a deferred-transfer-mode partner-package booking, transferToOperator() is not called at all. Instead, two independent transfers replace what the destination charge used to conflate into one lump sum:
  • transferSellingCommission() (new) — sends the selling tenant only their configured Partner Fee. If that fee is 0, no Stripe call is made and no ledger row is written; the selling tenant gets nothing for this booking.
  • transferToPartner() — unchanged, sends the 3rd party their ticket cost independently, exactly as it already does today.
Because the selling tenant is never routed the ticket-cost portion under this design, there is nothing left to reconcile back out of their account — the double-disbursement risk the earlier draft flagged as Decision 6 doesn't arise in the first place. NAT's own service commission is never transferred to anyone, in either case. Regression-tested: tests/Unit/TransferPayment/TransferToOperatorTest.php's test_partner_package_booking_with_nonzero_partner_fee_pays_both_selling_tenant_and_third_party and test_partner_package_booking_with_zero_partner_fee_pays_only_third_party, plus reversal coverage (reverseSellingCommissionTransfer(), including the no-op case when the fee was 0).
Separate pre-existing bug found, unrelated to 2027 A same-tenant cart combining packages from two different tour_operator_id rows, paid through the "raw manual card entry" path (createPaymentIntentForCart() → CardBookingService::run()), has zero is_partner_package/transferToPartner() handling at all — it would silently skip the 3rd-party payout entirely. The sibling path where the client pre-creates the PaymentIntent (createComboBookingCard()) handles this correctly, looping per cart item. Flagged for its own separate fix; unrelated to this migration.

Also confirmed directly: there is no cross-tenant-database combo cart capability today — "partner package" always means a package physically stored in the selling tenant's own database, routed to a different Stripe account by column, never a live join across two tenants' databases in one checkout.

7.3 Operator & selling-commission transfer engine shipped

Done. Per Decision 1 (resolved — Section 1/3/12), this is not a scheduled sweep; it is four new static methods on the existing App\Services\TransferPayment\TransferPaymentService, called synchronously from the exact same trigger points transferToPartner() already uses today (Section 6.6):

  • transferToOperator(array $data): bool — for a non-partner booking only. Mirrors transferToPartner()'s math with the partner-fee subtraction dropped (payoutAmount = amount - platformFees), calls createTransfer(), records a transfers row with transfer_type='primary_operator'.   • transferSellingCommission(array $data): bool — for a partner-package booking's selling tenant. Sends only the configured Partner Fee ($data['partner_fees']) — not the full remainder. Same try/catch-and-log failure handling as transferToOperator().
  • reverseOperatorTransfer($tourBookingId, $transactionId, $amount) / reverseSellingCommissionTransfer(...) — the transfer_type-filtered reversal counterparts, each with the same over-reversal guard as the existing reverseTransfer(). 7.11 Destination-charge transfer description/metadata shipped

Real gap found by the user testing live, not by this project's own review: viewing a transfer in a connected account's own Stripe dashboard showed no description and no metadata at all. Investigated by first re-verifying this codebase's own explicit Transfer::create() calls (all six, in TransferPaymentService — transferToPartner(), updatePartnerTransfer(), transferBetweenConnectedAccounts(), transferToNewPartner(), transferToOperator(), transferSellingCommission()) — confirmed by reading every one that description/metadata are already present and have been for a long time (git history shows transferToPartner()'s own description/metadata predate this entire 2027 project). Confirmed empirically, not just by code review: created a real transfer against a real test-mode Stripe account with the exact same param shape this codebase already sends, then retrieved it back — description and metadata both came back exactly as sent. These six call sites needed no fix.

Root cause, also confirmed empirically: created a real destination charge (the model virtually every booking uses today — transfer_data.destination + application_fee_amount, Section 4.1) against the same test account and inspected the result. The Charge object correctly carried the description/metadata the PaymentIntent was created with — but the Transfer object Stripe creates automatically as a side effect of that charge came back with description: null, metadata: [], every time. This is a genuine Stripe platform behavior, not a bug in any of this codebase's own code: Stripe's transfer_data parameter only accepts amount/destination, with no way to set the resulting transfer's own description or metadata at creation time. The only way to enrich it is a follow-up Transfer::update() call once the transfer's id is known — and since virtually every booking today still settles via a destination charge (deferred-transfer mode is barely enabled anywhere yet, Section 7.10), this gap affected the overwhelming majority of live transfers, not an edge case.

First implementation attempt, corrected same revision by the user before finalizing: initially centralized this at the payment_intent.succeeded Stripe webhook (StripeWebhookController::handleStripePaymentIntentSucceeded()), reasoning that unlike transferToOperator()/transferSellingCommission() (which must never rely on a webhook, to avoid a double-transfer race on real money movement), pure metadata attachment is idempotent and side-effect-free, so a webhook's "fires for every succeeded PaymentIntent" property seemed like a safe, minimal-footprint win. The user corrected this: this app's payment_intent.succeeded webhook plumbing (the metadata.section/app-gated dispatch it's built around) was developed specifically for the mobile application's own payment flows, and the application is currently closed — so leaning on Stripe webhook delivery at all, for anything, cannot be trusted as a reliable mechanism right now, regardless of how the code reads. This is exactly the kind of operational/infrastructure fact no amount of code reading reveals — corrected immediately rather than defended.

Implementation, rebuilt around a queued Laravel Job instead — centralized in ONE place, but a place this project's own architecture already trusts and already relies on synchronously, not Stripe's webhook delivery: App\Services\Booking\TransactionService::storePaymentInTransaction() and its three siblings (storeAddonsPaymentInTransaction(), storeCustomChargeInTransaction(), storeTipInTransaction()) — the same four shared methods this whole project's payment_mode column already threads through ~40+ callers, the one genuinely common choke point every Card confirmation flow in the codebase passes through synchronously, no webhook involved. Second real gap, found by the user testing live, same revision: a REAL booking's connected-account "Payments" view (a py_-prefixed dashboard entry) still showed no description/metadata, even after the fix above. 12. Open Decisions Needed

Decision 1 — RESOLVED: transfer fires immediately, synchronously Confirmed: the operator's share moves the instant the charge is confirmed, same timing as a destination charge today — no delay, no scheduled job, no "hold until tour date/cancellation window" behavior. The engine is built accordingly (Section 7.3).
Decision 2 — RESOLVED: combo-cart mode rule "Any row ≥ 2027 forces the whole cart to deferred mode" (Section 5.3) is implemented in PaymentModeResolver and regression-tested. No objection raised — proceeding as shipped.
Decision 3 — RESOLVED: ledger table shape The existing transfers table was extended with a transfer_type discriminator (Section 8) rather than creating a new table. Shipped.
Decision 4 — RESOLVED: per-tenant kill-switch Per-tenant, chosen over global specifically because every tenant has its own Stripe Connect account with its own capability/restriction state — a per-tenant gate contains a problem to the one tenant that has it rather than forcing an all-or-nothing choice for everyone, and matches how tenants will actually open their 2027 calendars on separate schedules. Shipped (Section 7.10): a tenant-scoped DEFERRED_TRANSFER_ENABLED setting, same mechanism as the pre-existing AUTO_PAYOUT toggle, checked once inside PaymentModeResolver so no call site can bypass it. Defaults OFF everywhere; explicitly enabled for dixies only.
Decision 5 — RESOLVED: operator + partner-split interaction Business-confirmed design (Section 6.7): for a partner-package booking, transferToOperator() is not called. Instead transferSellingCommission() sends the selling tenant only their configured Partner Fee, and transferToPartner() runs additionally, completely unchanged, sending the 3rd party's ticket cost independently. Regression-tested in TransferToOperatorTest's partner-package tests, including the zero-Partner-Fee case.
Decision 6 — RESOLVED: no ticket-cost double-disbursement An earlier draft of this plan (before the correction above) would have sent the selling tenant the full remainder via transferToOperator(), which really would have disbursed the ticket cost twice with nothing reconciling it back out. The corrected design in Decision 5 sends the selling tenant only their own Partner Fee — never the ticket-cost portion — so this risk doesn't arise under the new model. (Whether today's existing destination-charge-based flow has the same underlying question is a separate, pre-existing matter this plan doesn't need to resolve to proceed, since the new model is built correctly from the start.)
