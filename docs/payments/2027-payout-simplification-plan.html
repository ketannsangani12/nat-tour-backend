1. Executive Summary

Today, every card, card-reader, and payment-link charge on the platform is created as a Stripe destination charge: the PaymentIntent carries transfer_data.destination and application_fee_amount, and Stripe automatically splits and pays the tour operator's share into their connected Stripe account the instant the charge succeeds. Payout Simplification changes this for any booking whose tour date falls on or after 2027-01-01: the full charge instead lands on the platform's own Stripe balance, with no automatic split at all. The operator is paid later, on whatever schedule their tenant already runs, through the existing Auto Payout system — unchanged in mechanism, simply now also aware that a platform-held transaction never landed money in the operator's account in the first place.

This is deliberately a smaller change than it might sound. A related, more ambitious idea — an instant per-booking Stripe Transfer to the operator, fired synchronously at charge time — was explored on a sibling branch (docs/payments/stripe-2027-transfer-plan.html) and shelved in favor of this project, because Payout Simplification needs none of that new machinery: no per-booking Transfer, no per-booking transfer-reversal-on-refund logic, no transfers ledger table. The only thing that changes at charge time is which Stripe parameters are sent — everything downstream (refunds, cancellations, disputes, and ultimately how the operator gets paid) continues to work off the same transactions table it always has, just reading a new payment_mode column to know which shape the original charge actually was.

Scope confirmation This round covers card, card-reader (Stripe Terminal), and payment-link charges only, gated purely by tour date. Guest tips are explicitly excluded from this round regardless of tour date (Section 3). Building the "pay the operator for a platform-held booking" leg of Auto Payout is also explicitly a future round — this round's job is to make sure Auto Payout does not mis-pay in the meantime (Section 11), not to build the new payout mechanism itself.
Confirmed — clean forward cutover, gated by a kill switch No 2027-dated booking has been sold on any tenant yet, so there is no historical platform-held transaction to reconcile or backfill — every booking today, and every booking created before this ships fleet-wide, keeps running on the existing destination-charge model unchanged, forever. The feature is additionally gated by a per-tenant PLATFORM_HELD_PAYOUT_ENABLED kill switch that fails closed (Section 5), so the 2027-01-01 boundary itself is not the real rollout gate — enabling the setting, tenant by tenant, is. A real near-miss with this exact setting (Section 9) is why that distinction matters in practice, not just in theory.
The finding that mattered most this round An earlier verification pass concluded the guest-facing statement descriptor (the tour operator's own name, never the platform's) would work correctly in every country under the new model, including Canada, without any extra logic. That conclusion was wrong, and was only caught because a real Stripe Dashboard screenshot showed a blank descriptor on a stalled test transaction. Section 8 documents the mistake, the correct mechanism, and the fix — in full, not glossed over — because it is the clearest example in this project of why "it worked in a quick test" and "it was verified against a real completed charge" are not the same claim.

2. Current Architecture — Destination Charges

All card-based money movement funnels through App\Contracts\Payments\PaymentGatewayInterface, implemented by App\Services\Payments\StripePaymentGateway, resolved via app(PaymentGatewayInterface::class) throughout repositories and services. The connected-account parameters for any given charge are built by one centralized method, buildConnectedPaymentData(string $destinationId, int $feeAmountCents, ?string $statementDescriptor, string $mode), which every PaymentIntent/Checkout-Session-creation call site is expected to call rather than assembling transfer_data/application_fee_amount/on_behalf_of by hand.

For today's destination-charge mode (still the only mode for pre-2027 tour dates, and for every booking until a tenant's kill switch is turned on), that method returns:

$data = [
    'application_fee_amount' => $feeAmountCents,
    'transfer_data'          => ['destination' => $destinationId],
];
// on_behalf_of requires card_payments capability; omitted for accounts that only have transfers (e.g. Canada)
if ($this->connectedAccountHasCardPayments($destinationId)) {
    $data['on_behalf_of'] = $destinationId;
}
if ($statementDescriptor !== null) {
    $data['statement_descriptor_suffix'] = $statementDescriptor;
}

Refunds against a destination charge send reverse_transfer/refund_application_fee so Stripe pulls back the corresponding slice of the automatic transfer and fee at the same time. Disputes lost against a destination charge automatically reverse the transfer as part of Stripe's own dispute-loss handling. None of this changes for any pre-2027 booking, on any tenant, regardless of whether that tenant's kill switch is on — the mode is decided per booking, at charge-creation time, not per tenant globally.

3. Scope & Locked-In Decisions

3.1 Mixed-date carts follow the later date

A single cart/PaymentIntent can bundle multiple bookings, each with its own tour date. PaymentModeResolver::resolve(iterable $tourDates) is conservative: if any date in the cart is 2027-01-01 or later, the whole charge settles as platform-held. Stripe cannot split one charge's settlement two ways, and treating an earlier-dated item as platform-held is the safer direction to be wrong in — the operator is paid slightly later via Auto Payout rather than a pre-2027 item being silently destination-charged when it shouldn't be.

3.2 Tips are excluded from this round entirely

Every tip-collection call site — StripeUtils::getStripeAttributesForAppTapToPay() and getStripeAttributesForCreateTip() — passes mode: PaymentModeResolver::DESTINATION explicitly and unconditionally, regardless of tour date. This was tightened during this round specifically so it reads as a deliberate decision in the code, not an accident of both methods happening to predate the $mode parameter's default. Tips stay on today's destination-charge model until a separate, later round makes an explicit decision to change that.

3.3 Auto Payout's own payout mechanism is not part of this round

This round makes sure a platform-held transaction is excluded from Auto Payout's existing sweep (Section 11) — it does not build the mechanism that will eventually pay the operator their share of a platform-held booking. That is intentionally deferred to a future round, once there is real production experience with platform-held transactions accumulating.

4. Target Architecture — Platform-Held Settlement

For a platform-held charge, buildConnectedPaymentData() omits transfer_data and application_fee_amount entirely — the full amount simply stays on the platform's Stripe balance, exactly as if the connected account didn't exist. The one thing that must survive unchanged is the guest-facing statement descriptor: the guest must see the tour operator's own name, never the platform's, on every booking regardless of settlement mode or country. Section 8 covers exactly how that requirement is met and the mistake made along the way; the resulting code is:

if ($mode === PaymentModeResolver::PLATFORM_HELD) {
    $data = [];
    if ($destinationId !== '' && $this->connectedAccountHasCardPayments($destinationId)) {
        $data['on_behalf_of'] = $destinationId;
        if ($statementDescriptor !== null) {
            $data['statement_descriptor_suffix'] = $statementDescriptor;
        }
    } elseif ($statementDescriptor !== null) {
        $data['statement_descriptor'] = $statementDescriptor;
    }
    return $data;
}

5. The 2027 Gate — PaymentModeResolver & Kill Switch

App\Services\Payments\PaymentModeResolver is the single place the 2027-01-01 boundary is expressed in code:

public const DESTINATION = 'destination';
public const PLATFORM_HELD = 'platform_held';
public const PLATFORM_HELD_STARTS_ON = '2027-01-01';
public const KILL_SWITCH_SETTING_KEY = 'PLATFORM_HELD_PAYOUT_ENABLED';

public function resolve(iterable $tourDates): string
{
    if (!hasSetting(self::KILL_SWITCH_SETTING_KEY)) {
        return self::DESTINATION;
    }
    foreach ($tourDates as $tourDate) {
        if ($this->normalizeDate($tourDate) >= self::PLATFORM_HELD_STARTS_ON) {
            return self::PLATFORM_HELD;
        }
    }
    return self::DESTINATION;
}

Two design choices are load-bearing and deliberate, not incidental:

  • Fails closed. A tenant with no PLATFORM_HELD_PAYOUT_ENABLED row at all (an un-migrated or not-yet-opted-in tenant) gets DESTINATION unconditionally — the resolver does not even look at the dates. Rollout is therefore tenant-by-tenant and explicit, never automatic just because a calendar date passed.
  • Decided once, never re-derived. Every call site resolves a mode at charge-creation time and writes it to transactions.payment_mode. Every later refund, cancellation, or dispute reads that column back rather than calling PaymentModeResolver again against the booking's current tour date — a booking's tour date can itself change (reschedule, switch package) after the original charge, so re-deriving later would silently disagree with what the original charge actually was. PaymentModeInference::fromStripeObject() exists for the few call sites that only have a raw Stripe object, not a Transaction row, in scope — it reads the object's own transfer_data/transfer presence as ground truth, which is a form of "read back what actually happened," not re-derivation from a date.
Real near-miss with the kill switch itself While writing this document, tenant dixies was found to already carry a PLATFORM_HELD_PAYOUT_ENABLED row with value=1 — left over from an unrelated, already-reverted proof-of-concept on a prior branch that happened to reuse this exact settings key. Because the Foundation migration only inserts its safe default when the key doesn't already exist, this stale enabled row silently survived. No real charge was misrouted (zero platform_held transactions exist on any tenant, and no 2027 booking has been sold), but it is a concrete demonstration of why Section 9's rollout checklist requires confirming the kill switch's live value on a tenant before treating the migration's default as sufficient. A fix-up migration (2026_09_18_000003_fix_stale_platform_held_payout_setting.php) resets any row whose comment doesn't match this feature's own canonical text back to 0.

8. The Canada Statement-Descriptor Investigation

The hard requirement behind this whole feature, stated by the business from the start, is that the guest must always see the tour operator's own name on their card statement — never the platform's — regardless of settlement mode or country. The mechanism for this is on_behalf_of: it marks the connected account as the entity the charge is "for," which is what determines whose name becomes the base of the statement descriptor. statement_descriptor_suffix only appends to whatever base was already selected by on_behalf_of — it cannot substitute for it.

8.1 The earlier, wrong conclusion

An earlier verification pass in this project tested whether a charge carrying on_behalf_of with no transfer_data at all — the exact shape platform-held mode needs — would succeed and correctly show the connected account's name, including against a Canadian test connected account (whose capabilities are {"transfers": "active"} only — no card_payments). Every test in that pass appeared to succeed. The conclusion drawn was that on_behalf_of works unconditionally with no transfer_data, regardless of card_payments capability, so buildConnectedPaymentData()'s platform-held branch could include on_behalf_of unconditionally whenever a destination ID exists, with no capability gate at all.

What was actually being tested Every one of those earlier test PaymentIntents either never had a payment method confirmed against it, or reached requires_action for 3D Secure and stopped there. Stripe does not run its on_behalf_of/card_payments capability check until it actually attempts to create the underlying charge — an unconfirmed or 3DS-stalled PaymentIntent never reaches that point. The earlier pass had verified that Stripe would accept the parameters at PaymentIntent-creation time, not that a real charge would complete with them.

8.2 How the mistake was caught

The user provided a real Stripe Dashboard screenshot of a test transaction stuck in an Incomplete state with a blank "Statement descriptor" field, and asked for proper re-verification in the CA test environment rather than trusting the earlier result. Re-running the test with off_session: true and an explicit confirm call — forcing Stripe past 3D Secure to a real, completed (or genuinely rejected) charge — surfaced Stripe's actual error for the first time:

You cannot create a charge with the `on_behalf_of` parameter set to a
connected account with `transfers` but without the `card_payments`
capability enabled.

This meant the earlier conclusion was backwards for exactly the accounts most likely to need the fallback: a Canadian connected account with only transfers capability would have every platform-held charge rejected outright the moment a real card was charged, not merely display an imperfect descriptor.

8.3 The correct mechanism, verified

statement_descriptor (the full override, as opposed to the suffix) is a property of the charging account — the platform's own account — not the connected account. It requires no connected-account capability at all, because Stripe never needs to check what the connected account can do; the platform is the one making the charge. buildConnectedPaymentData()'s platform-held branch was rewritten to gate on_behalf_of on connectedAccountHasCardPayments() (the same check the destination-mode branch already used) and fall back to a full statement_descriptor override — set to the tour operator's own name — when the connected account lacks the capability:

if ($destinationId !== '' && $this->connectedAccountHasCardPayments($destinationId)) {
    $data['on_behalf_of'] = $destinationId;
    if ($statementDescriptor !== null) {
        $data['statement_descriptor_suffix'] = $statementDescriptor;
    }
} elseif ($statementDescriptor !== null) {
    $data['statement_descriptor'] = $statementDescriptor;
}

Verified end-to-end with real, completed test charges (not just PaymentIntent creation) against both dixies (US, has card_payments — takes the on_behalf_of path) and aswta (CA, does not — takes the statement_descriptor fallback path), confirming the connected account's own name appears on Charge::calculated_statement_descriptor in both cases, never the platform's. Correction (Section 8.5): those charges called Stripe directly with the descriptor supplied; the booking code paths did not supply it until October 6, 2026.

8.4 Why the pre-existing stripOnBehalfOfForCountry() helper is unrelated

app/helpers.php's stripOnBehalfOfForCountry(array $params, string $mode) predates this project by about four months — traced via git log --follow -p to commit 7ba28a9, "hotfix for Canada" (May 18, 2026), a real production fix for a completely different problem: Stripe rejecting cross-border on_behalf_of specifically when paired with transfer_data for a Canadian connected account. Its original test tenant, mahikan, no longer exists in the system; aswta is now the only Canadian tenant. It is called from exactly two places — CustomerController.php's tip link and PaymentLinkService::createPaymentLink() — and only strips on_behalf_of when $mode === PaymentModeResolver::DESTINATION, which is exactly its original, unchanged behavior for every pre-2027 booking. It plays no role in the platform-held fix above; the two are separate mechanisms solving two different Stripe rejections that happen to both involve Canada.

Net effect for Canadian operators under platform-held mode A Canadian tour operator's guests see the operator's own name on their statement exactly as they do today — via statement_descriptor instead of on_behalf_of + suffix, a mechanical difference invisible to the guest. No business/requirements conversation was needed once the correct mechanism was identified; it was a straightforward code fix, confirmed working against a real account. Correction (Section 8.5): this held for Payment Links only until October 6, 2026.

8.5 Correction (October 6, 2026): the fix reached Payment Links only

Sections 8.3 and 8.4 describe the mechanism correctly but overstate where it was applied. The rewritten branch of buildConnectedPaymentData() produces a full statement_descriptor only when the caller passes the operator's descriptor to it as an argument. Of the 19 call sites, only PaymentLinkService::createPaymentLink() does. The other 18 — online card, POS, card reader (web and mobile app), and the V1/V3 booking repositories — set statement_descriptor_suffix on their own base payload and pass no descriptor to the helper, so for a platform-held charge on an account without card_payments the helper returned nothing for the descriptor. This was equally true at commit 422dc3ddf.

Why it was missed StripePaymentGatewayModeTest calls the helper directly and hands it a descriptor ('MY TOUR CO'), and the "end-to-end" charges in 8.3 were created by calling Stripe directly, so neither exercised the real booking code. Reproduced on October 6, 2026 in Stripe test mode with the real call-site shape on aswta, sent straight to Stripe: the guest statement was TOURS* ASWTA — the platform's own name (the platform's static descriptor is TOURS).

The fix. It is applied once, at the single place every card PaymentIntent is created: StripePaymentGateway::createPayment() now calls the new PlatformChargeStatementDescriptor::normalize(). That rewrites only a charge made directly on the platform account — no transfer_data, no on_behalf_of, no stripe_account option — moving the operator's name from statement_descriptor_suffix into a full statement_descriptor, cleaned to Stripe's rules (no < > \ ' " *, 5 to 22 characters, at least one letter). Destination charges, on_behalf_of charges and direct charges on a connected account are returned untouched. If both a suffix and a full descriptor are sent, Stripe uses the suffix, so the suffix is removed, not supplemented. PaymentLinkService is unchanged.

Limits to know about Docs vs. behaviour. Stripe's documentation says a full statement_descriptor is for non-card payments only; in test mode it is accepted for card charges, online and Terminal, and replaces the whole line. A sandbox test fails loudly if that changes; live mode is re-checked at go-live. Short names. A name under 5 characters cannot be a valid full descriptor, so the suffix is kept and the platform prefix would show; the only such account in the development database, aswta, is exactly 5 characters. Checkout. A completed hosted Checkout charge has still not been walked end-to-end, though Stripe stores the descriptor on the PaymentIntent.

9. Live Production Incidents Found Along the Way

None of the following are Payout Simplification bugs — all three predate this project — but all three were found only because this project required reading every refund/cancellation call site closely enough to notice something didn't reconcile. Recorded here because they were fixed in the same branch and window of work.

9.1 "Cannot reverse transfer on charge ... it does not have an associated transfer"

A cancellation attempt failed outright because a raw ledger-write call site had never recorded payment_mode at all, defaulting to 'destination' for a charge that Stripe never actually gave a transfer to reverse. Root-caused to the same class of gap fixed comprehensively in Section 6.5 and 9.3 below — a raw DB::table('transactions') insert or a TransactionService call missing its mode.

9.2 "Refund amount ($180.49) is greater than unrefunded amount on charge ($102.92)" & the $94.47-vs-$86.02 follow-up

TicketRefundCancelService.php's net-refund calculation added a "kept fee" bookkeeping figure ($oldRefundKeepUs, a pure reporting artifact from an unrelated pax-removal code path, never actually refunded to the guest) back into a real Stripe refund amount instead of only netting out the prior refund:

// before
$net_amount = $transTicketCost + $oldRefundKeepUs;
// after
$net_amount = $transTicketCost - $ref;

A structurally identical bug in WeatherRefundCancelService.php required netting out both the prior refund and a previously-kept fee ($alreadyKeptFee, summed from the booking's own RefundHistory rows) — an initial fix that only subtracted the prior refund still overpaid, caught by the user re-deriving the expected number by hand from the booking's real history before accepting the fix.

9.3 payment_mode silently defaulting to 'destination' on every cancellation refund

Covered in full in the Revision History and Section 6.5 — CancelTransactionUpdateService::run() never set payment_mode at all across any of its 29 call sites, so every cancellation refund row silently inherited the DB column's 'destination' default. 8 already-wrong rows on kens were found by cross-referencing status='Refund' rows against sibling status='Completed' rows sharing the same transaction_number, and corrected directly in production.

10. The fee_amount / application_fee_id Correction

Scope, as clarified directly by the business owner mid-task after an initial broader framing was corrected: fee_amount/application_fee_id must be stored as null — never 0 or an empty string — whenever a refund type deliberately does not refund the platform's fee (Ticket Refund, Don't Refund, Partial Refund). A genuine 100%/Full Refund, which does refund the fee, must keep storing its real value, and was explicitly confirmed already correct and out of scope for this change.

Fixed at the shared-method level rather than auditing every call site individually, given the caller count (71 across the two TransactionService refund methods alone) — a deliberate trade-off favoring completeness over per-site precision:

// CancelTransactionUpdateService::run()
$feeAmountToStore = ((float) ($feeAmount ?? 0)) > 0 ? $feeAmount : null;
$applicationFeeIdToStore = ($feeAmountToStore !== null && $applicationFeeId !== '') ? $applicationFeeId : null;

The same pattern (a local computed value replacing the raw input before the write) was applied inside TransactionService::storeRefundInTransaction(), storeAddonsRefundInTransaction(), and storeCustomChargeRefundInTransaction(). 6 new tests in TransactionServiceTest.php and 3 in CancelTransactionUpdateServiceFeeAmountTest.php cover the null-input, zero-normalized-to-null, and genuine-non-zero-fee-preserved cases for each method.

11. Auto Payout Exclusion

Auto Payout pays operators via a real Stripe Connect payout drawn from their own connected-account balance. A destination charge auto-populates that balance via transfer_data the moment it succeeds; a platform-held charge never does — the money stays on the platform's own balance instead. PayoutApprovalService::calculateAccountPayoutAmount() and its siblings compute a payout amount by summing local transactions/tour_bookings_master rows, with no inherent awareness of which settlement model produced any given row.

Three query sites carry an explicit payment_mode filter for exactly this reason:

->where('tra.payment_mode', PaymentModeResolver::DESTINATION)
FileMethod
app/Services/PayoutApprovalService.php:109calculateAccountPayoutAmount() (or equivalent computation query)

app/Http/Controllers/Admin/AutoPayout/AutoPayoutController.php:637Admin-facing payout preview/execution query
Why the live-balance check alone isn't sufficient PayoutApprovalService::executeImmediatePayout()/executeSinglePayout() also check the connected account's live Stripe balance (Balance::retrieve(['stripe_account' => $stripeAccountId])) before sending a payout, as a blunt "don't overdraw" safety net. That check is unaware of where the balance came from — if the account happens to hold unrelated legitimate balance (a prior destination-charge booking, a manual top-up), it would not by itself catch a platform-held transaction being incorrectly included in the computed payout amount. The payment_mode filter above is the actual correctness fix; the balance check is a separate, coarser safety net that remains valuable but was never a substitute for this filter.

Building the mechanism that eventually does pay the operator their share of a platform-held booking (whatever that ends up looking like — likely a new Auto Payout leg once real production experience with platform-held transactions exists) is explicitly future work, not part of this round.

17. Appendix B — Stripe Connect Glossary

TermMeaning
Destination chargeA PaymentIntent created on the platform account with transfer_data.destination set; Stripe automatically splits and transfers funds to the connected account the moment the charge settles. Still the model for every pre-2027 booking, and every booking on a tenant with the kill switch off.
Platform-held chargeThis project's term (not a formal Stripe product name) for a plain platform charge with no transfer_data/application_fee_amount at all — the full amount stays on the platform's own balance until moved later by a separate mechanism (here, Auto Payout, on its normal schedule).
on_behalf_ofMarks the connected account as the entity the charge is "for" — determines the base of the guest-facing statement descriptor and shifts some card-present liability. Requires the connected account to have card_payments capability active, even with no transfer_data present — the mistake corrected in Section 8.
statement_descriptor_suffixAppends to whatever descriptor base on_behalf_of already selected. Cannot substitute for on_behalf_of — without it, there is no operator-name base for the suffix to append to.
statement_descriptor (full override)A property of the charging (platform) account, not the connected account — replaces the descriptor entirely, independent of on_behalf_of and requiring no connected-account capability at all. The fallback mechanism for accounts without card_payments (Section 8.3).
card_payments capabilityA connected account capability, separate from transfers. Most Canadian operators on this platform have only transfers active, not card_payments — the reason the Section 8 fallback exists at all.
application_fee_amountOn a destination charge, the slice the platform keeps; the rest transfers automatically. Omitted entirely for platform-held charges — meaningless once there's no automatic split to take a slice of.
reverse_transfer / refund_application_feeRefund-time flags meaningful only against a destination charge. Stripped by buildRefundParams() for platform-held mode — sending either against a charge that never had transfer_data would error.
