01 — The short version

What this plan is about

From 2027, when a guest pays by card, the whole amount stays in NAT's Stripe balance. The tour operator is not paid automatically any more. Today, nothing sends operators that money yet. This plan builds the part that does.

The problem

Auto Payout only knows how to pay out money that already sits in the operator's own Stripe account. 2027 money never gets there, so Auto Payout deliberately skips it. Without a new module, 2027 operators would never be paid.

The answer

A new module, Operator Payments. It finds every 2027 payment that is ready, works out exactly what each operator is owed, lets an admin approve it, moves the money to the operator's Stripe account, then sends it to their bank.

What makes it trustworthy

  • Each payment is counted once. The system itself refuses to pay the same payment twice.
  • One calculation, same as today. It gives the same answer as Auto Payout for the same bookings — we test this on purpose.
  • Refunds and disputes are handled automatically — before or after the operator is paid.
  • Preview mode first. We run it for several cycles without moving any real money and compare the results.
  • NAT keeps only its own fee. All ticket cost goes to the operator — no safety deposit and no minimum balance is held back.
  • Built for non-technical staff: plain words, a "Why this amount?" explanation on every line, and clear next steps.

02 — What changes in 2027

Where the money goes

Until the end of 2026 Stripe splits every card payment the moment it happens. In 2027 it doesn't — so something has to carry the money onward.

Why not just extend Auto Payout?

Auto Payout pays from the operator's own Stripe balance, and it tracks "paid / not paid" for a whole booking. 2027 money needs an extra step first (moving it into that balance), and it is safer to keep the tried-and-tested 2026 payout untouched. So the new module sits beside it, reuses its rules (schedule, waiting days, minimum and maximum amounts, notification emails, approval) and follows its calculation — but keeps its own records.

In plain words Operators will see two deposits at first: the usual Auto Payout, and a separate one labelled for 2027 bookings. They can be merged into one later, once everything has proven itself.
03 — How a payment run works

From "ready" to "in the bank"

Each time the schedule comes round, the module prepares a payment run for the operator. Nothing real happens until an admin approves it.

If something goes wrong halfway

Moving the money and sending it to the bank are two separate steps, each remembered separately. If the first works and the second fails, the money simply waits safely in the operator's Stripe account and only the bank step is retried. The money is never moved twice.

To be proven, not assumed How quickly moved money becomes available for the bank payout depends on Stripe. We will measure it in Stripe's test mode before any real operator is paid; if it isn't instant, the run simply waits and retries.
04 — When does an operator get paid?

Two ways to decide the date

Each operator gets one setting: pay by tour date or by purchase date, plus a number of days to wait.

Tour date + days

A payment becomes ready a few days after the tour happens. This is how Auto Payout works today. Safest for refunds, slower for the operator.

Purchase date + days

A payment becomes ready a few days after the guest paid, even if the tour is months away. Faster for the operator. If the guest is refunded later, it is deducted from the operator's next payment (agreed).

Shared rules for both options

  • The schedule (daily, weekly, monthly), minimum amount, maximum amount, start date and notification emails come from the operator's existing Auto Payout rule — nothing new to set up there.
  • Only card payments are included. Cash, invoiced and tip payments are not.
  • Payments that would need a refund-sized deduction larger than the next payment simply wait: the run is skipped and the amount carries forward until it is covered.
  • If an operator's date setting is changed, it applies to payments not yet paid. Payments already paid are never re-opened.
05 — How the amount is worked out

One rule, applied to every payment

For each card payment: operator is owed what the guest paid minus NAT's fee. For each refund: the operator gives back what they would have received for it. Add them all up — that is the payment.

The rules behind the numbers

  • Cents, not decimals. All maths is done in whole cents, so a rounding error can't creep in.
  • One calculation, in one place. Today's Auto Payout repeats its formula in three places, which is where mistakes hide. The new module has a single calculator that everything else uses.
  • Each payment on its own line. Every payment and every refund is its own record. A refund after payment becomes a deduction on the next run, with no special "adjustment detection" needed.
  • Booked, then cancelled with no refund? The operator keeps the money — same as Auto Payout today.

07 — How NAT stays protected

NAT keeps only its fee

Every dollar of ticket cost goes to the operator. No safety deposit is held back and no minimum balance is kept aside — NAT's balance keeps only NAT's own fee.

Four protections that don't hold anyone's money

1

Later refunds come off the next payment

If a guest is refunded after the operator was paid, that amount is deducted from the operator's next payment. If it is bigger than the next payment, it carries forward until it is covered.

2

Lost disputes are deducted the same way

For operators with the Dispute Reversal setting. NAT absorbs its own fee, exactly as it does today. Disputes that are won or still open change nothing.

3

Money moves only when it is really available

Recent card payments take a few days to clear in Stripe. Until then the run shows Waiting for funds and retries by itself. Nothing is ever half-paid. (To be confirmed in Stripe test mode.)

4

A daily check compares what NAT holds with what NAT owes

If NAT's balance would not cover what it owes operators, an alert goes out. It only warns — it never holds money back.

The trade-off you chose With no safety hold, a refund or lost dispute that arrives after an operator was paid is covered by NAT first and recovered from that operator's next payment. If an operator stops taking bookings, there may be nothing left to recover from. A safety hold could be added later without redesigning anything.

09 — How we make sure the numbers are never wrong

Seven safeguards

Getting money wrong costs trust, so the design assumes mistakes will be attempted — and blocks them.

Each payment is paid once — enforced by the database

Every payment and refund gets one record that can exist only once. Even a software bug can't make the system pay the same payment twice.

The same answer as Auto Payout

A standing test feeds identical bookings to today's Auto Payout calculation and the new one and requires the result to match to the cent. A difference fails the build.

Preview mode before real money

For several cycles the module calculates and stores runs without touching Stripe. We compare them against an independent recalculation from Stripe's own payment and refund records.

A person approves every run (version 1)

Nothing moves without an admin's approval, a maximum amount per run can be set, and every action is recorded with who and when.

Safe to retry, never moves twice

Every Stripe action carries a unique key, and each step is remembered. A crash or timeout can be retried without any risk of a duplicate. A recovery tool finds any Stripe action that wasn't recorded.

A daily check: "What NAT holds vs. what NAT owes"

Every day the module confirms that every 2027 payment is accounted for exactly once, that each booking's total is right, and that Stripe's records match NAT's. It also shows whether NAT's balance covers what it owes operators, and alerts if not.

Test money first — production is not touched

Until you say go-live, only Stripe test (sandbox) keys are used. The module refuses to run with a live Stripe key unless a super admin has deliberately unlocked Live.

10 — Partner bookings

Paid the same way as any booking

Partner (3-way) bookings split a payment between the operator and a partner. Another developer, Ketan, is changing this for 2027 on the branch feature-partner-commision-simplification.

What that branch does
  • From 2027-01-01, for every operator, the partner's share is no longer sent through Stripe.
  • It is only recorded in the payouts table, with an empty transfer id.
What it means for Operator Payments
  • The operator is owed payment − NAT fee — nothing else is taken off.
  • This module does not deduct or pay the partner's share.
Decided For a partner booking the operator is owed payment − NAT fee, with nothing else deducted. Operator Payments does not pay the partner.
Worth knowing Because this module does not pay partners, the partner's share — recorded by Ketan's branch — has to be settled separately, outside Operator Payments. Ketan's deletion of app/Services/UnitTest/UnitTest.php (364 lines) has been confirmed as intended.

Appendix — for developers

Technical notes

Skip this page if you are not building it. Everything above is the product; this is how it is anchored in the code.

New records

TablePurpose
settlement_batchesOne payment run per operator and Stripe account; status, totals, period, Stripe transfer and payout ids, retry state.
settlement_itemsThe payment record: one row per transaction, UNIQUE(transaction_id); signed amount in cents; owed-to account; kind (payment, refund, adjustment, dispute).
settlement_adjustmentsManual corrections and lost-dispute deductions (credit/debit, pending/applied/voided).
settlement_batch_logsAudit trail of every action; not cascade-deleted.

Naming avoids payouts (partner ledger) and transfers (used on the shelved deferred-transfer branch).

Key design points

  • Per-row owed amount = ±(amount − fee_amount) in integer cents; one SettlementCalculator; parity test against PayoutApprovalService::calculateAccountPayoutAmount.
  • Eligibility: Completed/Refund, via='Card', payment_mode='platform_held', not request_from='Insert', no # comments; release = tour datetime or created_at + days (per-tenant setting). No lower date bound, so no "orphaned" bookings.
  • Execution: global Redis lock → platform Balance::retrieve (available, per currency; transfer ≤ available, otherwise Waiting for funds) → createTransfer with idempotency key from batch reference → persist → bank payout (retry never re-transfers). No reserve or holdback. Live-key guard: refuse to run with a live Stripe key unless a super admin has unlocked Live.
  • Account resolution through a SettlementAccountResolver: returns the operator's account in version 1; package-level accounts later mean changing only this class. Batches are grouped by account so that change needs nothing else.
  • Disputes: hook StripeWebhookController lost-dispute path and manual mark-lost in DisputeService::updateDisputeStatus, gated by DISPUTE_REVERSAL, idempotent per dispute id.

Changes to existing code (small, but required)

  • StripeWebhookController::handleStripeAutoPayout: match settlement payouts first; add the payment_mode filter to its fallback branch (today it would create a bogus Auto Payout record and set payout_made=1).
  • PayoutAdjustmentService (3 detect methods): skip platform-held transactions, or refunds are counted twice.
  • PayoutApprovalService::recalculatePendingPayout: add the payment_mode filter.
  • ProcessAutoPayouts: run the settlement leg inside the same tick and lock; reconcile settlement payouts.
  • Central SettingController whitelist + validation for the new keys; permission for the master switch.
