01 · The Problem

Every code change waited in line

Before a developer's change can be approved and shipped, the system automatically re-checks the entire product — to make sure nothing broke. That check used to take about 20 minutes, every single time.

Whenever an engineer proposes a change — fixing a bug, adding a feature — GitHub automatically spins up a fresh, disposable copy of the booking platform and runs 1,604 individual checks against it (6,088 individual assertions in total). Each check asks a very specific question, for example:

Does a partial refund add up?

"Refund removed pax addons for rate group refunds matching pax items" — checks that removing one traveler from a group booking refunds exactly the right amount.

Does a customer's email get accepted?

"Customer email validation" — checks dozens of real-world email formats so a legitimate booking is never rejected at checkout.

Does a disputed charge notify the right people?

"Dispute notification service" — checks that a bank chargeback alerts the operator before the response deadline passes.

Does the money end up in the right account?

"Stripe application-fee rounding" — checks that a payment split across the platform and a tour operator never loses a cent to rounding.

An engineer opens a change, then waits. In practice that means either sitting idle for ~20 minutes, or context-switching to something else and losing focus — and across a whole team making many changes a week, that wait adds up fast.

02 · Quick Wins — Already Shipped

Two fixes, before touching parallelism

Before running checks side-by-side, we found two things making every single check slower than it needed to be — both fixed with no new risk.
01

A needless restart, every single check

For every one of the 1,604 checks, the system was fully restarting itself from scratch — not once, but twice — even though only about a fifth of the checks actually needed that second restart. It's the equivalent of closing and reopening an entire application twice, just to glance at one setting.

Fixed — one restart, only where needed
02

Re-downloading the same ingredients every time

The system was also re-fetching all ~167 external code packages it depends on, from the internet, from scratch, on every single run — instead of remembering what it fetched last time and reusing it.

Fixed — packages are now cached between runs

Result: measured, not estimated

03 · The Big Decision

Instead of one line, open more lanes

The two fixes made each check faster. The next lever is running many checks at the same time — like opening more checkout lanes at a store instead of one register for everyone. There are two different ways to do that.

A · Split Lanes

Live now

The 1,604 checks are split into 4 equal batches; each batch gets its own completely separate computer, with its own separate practice database.

Safety: zero chance one lane's data touches another's — by construction. Cost: setup is paid 4 times instead of once.

B · Shared Lanes

Not built yet

One computer runs 4 workers side by side, each working through its own slice of checks, inside the same environment.

Cost: only one computer to set up — cheaper. Safety: needs new engineering to guarantee workers never collide.

05 · What It Costs

A monthly allowance, not a per-minute bill

GitHub, who runs this automated checking system for us, works like a mobile phone data plan.

The plan analogy: the company's GitHub plan already includes a set number of computer-minutes every month, as part of what we pay today. Only minutes used above that included amount cost anything extra — the same way going over your phone's data cap is the only time it charges more.

Nothing has actually been charged, this month or any prior day

Every day shown above billed $0, even as raw usage climbed — the plan's monthly allowance absorbed all of it.

What turning on Split Lanes adds

Split Lanes is projected to add roughly 850 extra computer-minutes a month — about $5 of the kind of usage shown above, using this account's own observed rate. That is small next to the pattern above, and very likely to stay fully covered the same way — worth a quick double-check in Settings → Billing → Overview before scaling this further (for example, going from 4 lanes to 8).
